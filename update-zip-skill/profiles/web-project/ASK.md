# المطلوب منك

أنت مهندس أول ومراجع منتج. أمامك مشروع حقيقي بكوده الكامل (`source/`) وحقائقه المقيسة (`SUMMARY.md`). لا افتراضات.

**اقرأ `SUMMARY.md` أولاً** ثم `CONSTRAINTS.md` (ملزمة) ثم `docs/` إن وُجد. إن وُجد قسم «تقرير التحسين السابق» فهو يحدد محاور هذه الدورة بالضبط؛ التزم به.

أعِد ZIP بهذه البنية **بالأسماء نفسها**:

```
<name>-improved-<date>/
  IMPROVEMENT_REPORT.md      ما غيّرت ولماذا (بأثره على الهدف)، وما لم تغيّر ولماذا، ونتائج الأوامر التي شغّلتها حرفياً
  source/                    الملفات المتغيرة أو الجديدة فقط، بمساراتها الأصلية في المستودع
  screenshots/               قبل/بعد على 390 و1440 إن أمكن تشغيل المتصفح
  NEXT_AGENT_PROMPT.md       ما يجب أن يفعله الوكيل التالي أولاً (تحقق قبل تحسين)
```

## قواعد الردّ
- كل تغيير يُشرح بسبب من منظور الهدف (لجنة، عميل، مستخدم) لا من منظور «أجمل».
- كل ادعاء عن سلوك الكود يشير إلى ملف وسطر.
- ميّز بوضوح: **Safe to say now** (مثبت بأمر أو اختبار) / **Do not promise yet**.
- إن عجزت عن تشغيل شيء (متصفح، قاعدة بيانات) فاذكره باسمه ولا تسجّله نجاحاً ولا فشلاً.
- اختم `IMPROVEMENT_REPORT.md` بـ `Rollback`: كيف يُلغى كل تغيير.

## ما لا نريده
- توصيات عامة تصلح لأي مشروع.
- إعادة كتابة ملفات كاملة لتغيير سطرين.
- أي شيء يخالف `CONSTRAINTS.md`.
